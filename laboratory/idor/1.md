# Insecure Direct Object Reference (IDOR) on Bets History Endpoint via [Parameter Name]

## Summary
An Insecure Direct Object Reference (IDOR / BOLA) vulnerability was identified within the `[Insert Parameter, e.g., cda_id]` parameter of the `[Insert Path, e.g., /betting/bets-history]` endpoint. The server application fails to validate whether the resource identifier provided in the query string matches the identity of the authenticated session token, permitting horizontal cross-account data visibility.

## Step-by-Step Reproduction Instructions
1. Authenticate to the application as Account B and capture the unique resource tracking value: `[Account B ID String]`.
2. Terminate or switch contexts to Account A's authenticated session state.
3. Issue a request to the targeted endpoint using Account A's valid authorization headers, but swap the target query parameter to match Account B's identifier:
   `https://1win.com/[path]?[parameter]=[Account B ID String]`
4. Send the request ensuring tool rates remain under the 5 requests-per-second boundary.
5. Observe that the backend server allows Account A to access Account B's history details.

## Proof of Concept (PoC)
```http
GET /betting/bets-history?cda_id=[ACCOUNT_B_IDENTIFIER] HTTP/1.1
Host: 1win.com
Authorization: Bearer [ACCOUNT_A_VALID_TOKEN]
Connection: close
```
*Note: The response successfully returned transaction elements linking back exclusively to Account B, confirming a broken object authorization state.*

## Impact
An authenticated actor can systematically access the private profile histories or sensitive configuration logs of other users by altering parameter references. Depending on the exposed data properties, this can lead to an infringement of player privacy or account landscape mapping.

## Suggested Remediation
*   **Session-Based Authorization**: Implement strict server-side validation checks that compare the requested resource ID directly against the user context decoded from the active authorization token or session cookie.
*   **Indirect Reference Maps**: Use unpredictable, non-enumerable cryptographic hashes or randomized UUID structures for resource identification, ensuring that authorization state validation occurs continuously at the api layer before any database fetch happens.
